# Pokémon Sword 1.3.2 — Egg RNG → EggCreateParam → PML Crypto Trigger Timeline

Updated: 2026-09-18

Target:
- Pokémon Sword / Shield 1.3.2
- Sample: `main(3).elf`
- GNU Build ID: `a3b75bcd3311385aeed67fbeeb79cbb7bf02f471`
- Address notation: `main + offset`

---

## 1. Overall architecture

The egg-generation path is split into two RNG domains:

```text
Day Care Egg Generator
      │
      ├── eggSeed RNG
      │      ├─ Gender
      │      ├─ Nature
      │      ├─ Ability
      │      ├─ IV
      │      ├─ EC
      │      └─ Masuda / Shiny-Charm PID
      │
      ▼
EggCreateParam
      │
      ▼
PML Pokémon Constructor
      │
      ├─ if PID is still unresolved
      │      ↓
      │   PML Crypto Provider
      │      ↓
      │     PID
      │
      ├─ Height
      │      ↓
      │   PML Crypto Provider
      │
      └─ Weight
             ↓
          PML Crypto Provider
```

The key distinction is:

- `eggSeed RNG` is deterministic once the Day Care has cached the pending egg seed.
- `PML Crypto Provider` is called later, during final Pokémon construction, and obtains fresh random bytes from Nintendo's crypto API.

---

## 2. Stage A — Day Care creates a pending egg

Main Day Care update function:

```text
main+0x1401530
```

When the egg-generation roll succeeds:

```asm
main+0x14016E8
    MOV  W9,#1

main+0x14016EC
    STRB W9,[slot+0x300]
```

This means:

```text
slot + 0x300 = 1
```

The egg is now waiting for pickup.

Immediately afterwards:

```asm
main+0x14016F0
    BL   main+0xF28FE0

main+0x14016F8
    STR  X0,[slot+0x2F8]
```

`main+0xF28FE0` calls:

```text
nn::crypto::GenerateCryptographicallyRandomBytes(..., 8)
```

So:

```text
slot + 0x2F8 = 64-bit eggSeed
```

At this moment:

- egg-ready state exists;
- eggSeed exists;
- final child PK8 does not yet exist;
- final HeightScalar and WeightScalar do not yet exist.

---

## 3. Stage B — pickup starts egg construction

Pickup entry:

```text
main+0x14018C0
```

The function verifies the ready flag and consumes it.

The cached seed is loaded at:

```asm
main+0x1401A20
    LDR X1,[X8,#0x2F8]
```

and passed into:

```text
main+0xF28FC0
```

which initializes the egg-local RNG object.

The egg-local RNG object is at:

```text
main+0x25A83A8
```

with the analyzed initialization:

```text
state0       = eggSeed
state1       = 0x82A2B175229D6A5B
originalSeed = eggSeed
```

The breeding RNG callback is:

```text
main+0x1400C70
```

## 4. EggCreateParam generation

The pickup path enters:

```text
main+0x7893F0
    ↓
main+0x789500
    ↓
main+0x789770
```

`main+0x789770` is the main egg-specific parameter generator.

The approximate relevant fields in `EggCreateParam` are:

| Offset | Field |
|---:|---|
| `+0x10` | EC |
| `+0x18` | PID / PID sentinel |
| `+0x20` | Trainer ID32 |
| `+0x28` | Species |
| `+0x2C` | Form |
| `+0x30` | Gender |
| `+0x32` | Nature |
| `+0x34` | Ability policy |
| `+0x35` | PID policy / attempt count |
| `+0x36..` | IV fields |
| `+0x4A` | WeightParam |
| `+0x4C` | HeightParam |

For a normal egg:

```text
WeightParam = 0x0100
HeightParam = 0x0100
```

which means “generate normal random scalar later”.

---

## 5. eggSeed RNG consumption

Inside `main+0x789770`, the egg-local RNG is consumed by breeding logic.

Conceptually:

```cpp
EggRng rng(eggSeed);

gender  = GenerateGender(rng, species);
nature  = GenerateNature(rng, parents, items);
ability = GenerateAbility(rng, parentAbility);
ivs     = GenerateAndInheritIVs(rng, parents, items);
ec      = rng.Next(0xFFFFFFFF);
```

The exact number/order of calls depends on:

- species and form rules;
- fixed-gender / genderless rules;
- Everstone;
- both parents holding Everstone;
- Destiny Knot;
- Power Items;
- duplicate IV inheritance retries;
- language relationship;
- Shiny Charm state.

This means PID prediction requires replaying all preceding egg-RNG consumption exactly.

## 6. EC generation

EC is generated at:

```text
main+0x789C0C
```

The code calls the Egg Context RNG callback with:

```text
RNG(0xFFFFFFFF)
```

and stores the result at:

```text
EggCreateParam + 0x10
```

Therefore:

```text
eggSeed
   ↓
egg-local RNG
   ↓
earlier breeding RNG consumption
   ↓
main+0x789C0C
   ↓
EC
```

EC is deterministic from eggSeed + parent/context state.

## 7. PID branch

The egg-specific PID/shiny logic is around:

```text
main+0x789C20 .. main+0x789C88
```

The branch determines whether PID is generated by the egg-local RNG or deferred to the generic PML constructor.

### 7.1 Masuda / Shiny Charm

Conceptually:

```cpp
uint32_t rolls = 0;

if (parent1.language != parent2.language)
    rolls = 6;

if (hasShinyCharm)
    rolls += 2;

if (rolls > 0)
{
    for (uint32_t i = 0; i < rolls; i++)
    {
        pid = EggRng(0xFFFFFFFF);

        if (IsShiny(trainerId32, pid))
            break;
    }

    param.pid = pid;
}
```

The shiny check is:

```text
main+0x777350
```

with the usual Gen VIII relation:

```text
TID ^ SID ^ PID_hi ^ PID_lo < 16
```

So in Masuda and/or Shiny Charm modes:

```text
eggSeed RNG
    ├─ EC
    └─ PID candidate(s)
```

PID is already populated before the PML constructor runs.

### 7.2 Ordinary same-language egg without Shiny Charm

When the egg-specific PID roll count is zero:

```text
EggCreateParam+0x18 = 0x3FFFFFFFF
```

This is a PID-not-generated sentinel.

So:

```text
egg generator
    ↓
PID unresolved
    ↓
generic constructor must generate it later
```

## 8. Transition into the PML Pokémon constructor

After `main+0x789770` returns, the caller continues toward:

```text
main+0x777F40
```

The important call-site window is:

```text
main+0x789664
    BL main+0x789770

main+0x789668
    ; EggCreateParam is now complete

...

main+0x7896F0
    BL main+0x777F40
```

This is the exact transition:

```text
egg-specific deterministic generation
            ↓
EggCreateParam complete
            ↓
generic PML Pokémon construction
```

# 9. When does PML → Nintendo Crypto actually trigger?

This is the key timing question.

> It does **not** trigger when the egg merely becomes ready.
>
> It triggers only after the player starts receiving the egg and the generic Pokémon constructor reaches a field that still requires random generation.

So the precise timeline is:

```text
Day Care egg ready
    ↓
eggSeed cached
    ↓
wait
    ↓
player accepts egg
    ↓
main+0x14018C0
    ↓
main+0x789770
    ↓
EggCreateParam built
    ↓
main+0x777F40 / main+0x7667A0
    ↓
PML fallback/random-size field encountered
    ↓
PML wrapper
    ↓
Nintendo Crypto
```

The three important trigger points are different.

---

## 10. PML Crypto trigger #1 — ordinary PID

Only for:

```text
same-language parents
AND
no Shiny Charm
```

the PID is still the sentinel.

Inside the generic constructor:

```text
main+0x7667A0
```

the sentinel is detected and the path reaches:

```text
main+0x7668C0
```

which calls:

```text
main+0x7660B0
```

This wrapper performs:

```text
GetPmlCore()
    ↓
PmlCore + 0x280
    ↓
main+0x7D1320
```

and `main+0x7D1320` does:

```asm
SUB  X0,X29,#4
MOV  W1,#4
BL   nn::crypto::GenerateCryptographicallyRandomBytes
LDUR W0,[X29,#-4]
RET
```

Equivalent:

```cpp
uint32_t PmlRandomRaw32()
{
    uint32_t v;
    nn::crypto::GenerateCryptographicallyRandomBytes(&v, 4);
    return v;
}
```

That result becomes the ordinary PID.

### Trigger time

```text
player has already accepted the egg
AND
main+0x789770 has already finished
AND
generic constructor is resolving PID
```

So the PID crypto call happens during PK8 construction, not at egg-ready time.

---

## 11. PML Crypto trigger #2 — HeightScalar

Height is processed after PID resolution.

The constructor loads:

```text
EggCreateParam + 0x4C
```

at:

```text
main+0x766EFC
```

and calls the size resolver at:

```text
main+0x766F04
    BL main+0x7672E0
```

For the normal mode:

```text
HeightParam = 0x0100
```

`main+0x7672E0` enters the normal random-size path:

```text
main+0x767490
```

which conceptually performs:

```cpp
height =
    PmlRandomBounded(129) +
    PmlRandomBounded(128);
```

The bounded wrapper is:

```text
main+0x7660D0
```

which dispatches through:

```text
PmlCore+0x288
    ↓
main+0x7D1360
    ↓
nn::crypto::GenerateCryptographicallyRandomBytes
```

So HeightScalar is generated **during the generic constructor, after PID processing**.

---

## 12. PML Crypto trigger #3 — WeightScalar

Immediately after Height, the constructor loads:

```text
EggCreateParam + 0x4A
```

at:

```text
main+0x766F0C
```

then calls:

```text
main+0x766F14
    BL main+0x7672E0
```

Again, with:

```text
WeightParam = 0x0100
```

the normal path is:

```cpp
weight =
    PmlRandomBounded(129) +
    PmlRandomBounded(128);
```

using:

```text
main+0x7660D0
 -> PmlCore+0x288
 -> main+0x7D1360
 -> Nintendo Crypto
```

Therefore WeightScalar is generated **after HeightScalar**, still inside the same final construction pass.

## 13. Exact trigger order

### Ordinary same-language/no-Charm egg

The relevant PML-trigger order is:

```text
EggCreateParam complete
    ↓
PML constructor starts
    ↓
PID sentinel found
    ↓
PML Raw32
    ↓
Nintendo Crypto
    ↓
PID fixed
    ↓
HeightParam 0x100
    ↓
PML Bounded(129)
    ↓
Nintendo Crypto
    ↓
PML Bounded(128)
    ↓
Nintendo Crypto
    ↓
Height fixed
    ↓
WeightParam 0x100
    ↓
PML Bounded(129)
    ↓
Nintendo Crypto
    ↓
PML Bounded(128)
    ↓
Nintendo Crypto
    ↓
Weight fixed
```

Conceptually:

```text
#1 crypto draw → PID

#2 crypto draw(s) → Height part A, rejection possible
#3 crypto draw    → Height part B

#4 crypto draw(s) → Weight part A, rejection possible
#5 crypto draw    → Weight part B
```

The actual number of crypto API calls may exceed five because `Bounded(129)` can reject and redraw.

### Masuda and/or Shiny Charm

PID is already generated from eggSeed.

Therefore:

```text
EggCreateParam complete
    ↓
PML constructor starts
    ↓
PID already valid
    ↓
skip PID Crypto
    ↓
Height Crypto
    ↓
Weight Crypto
```

## 14. PML bounded crypto implementation

The bounded provider is:

```text
main+0x7D1360
```

Conceptual implementation:

```cpp
uint32_t PmlRandomBounded(uint32_t bound)
{
    if (bound == 1)
        return 0;

    if (bound == 0)
        return PmlRandomRaw32();

    uint32_t mask = NextPowerOfTwo(bound) - 1;

    for (;;)
    {
        uint32_t raw;
        nn::crypto::GenerateCryptographicallyRandomBytes(&raw, 4);

        uint32_t value = raw & mask;

        if (value < bound)
            return value;
    }
}
```

Therefore:

```text
Bounded(128)
    mask = 0x7F
    always succeeds after one 32-bit crypto draw

Bounded(129)
    mask = 0xFF
    accepts 0..128
    rejects 129..255
```

## 15. Height / Weight distribution

The normal formulas are:

```text
HeightScalar = Random(129) + Random(128)
WeightScalar = Random(129) + Random(128)
```

Each scalar is in:

```text
0..255
```

but the distribution is triangular rather than uniform.

For `S = 0..127`:

```text
P(S) = (S+1) / (129*128)
```

For `S = 128`:

```text
P(128) = 128 / (129*128)
```

For `S = 129..255`:

```text
P(S) = (256-S) / (129*128)
```

Extreme values:

```text
P(0)   = 1 / 16512
P(255) = 1 / 16512
```

So the crypto source is unpredictable, but the output distribution is fixed.

## 16. Final write into PK8

After the scalars are resolved, the constructor writes them into the final Pokémon data.

Height setter:

```text
main+0x775700
```

writes:

```text
PK8 + 0x50 = HeightScalar
```

Weight setter:

```text
main+0x775850
```

writes:

```text
PK8 + 0x51 = WeightScalar
```

After this point, Height and Weight are fixed and do not reroll at hatch.

## 19. Practical interpretation

The cleanest wording is:

> `eggSeed` decides the egg-specific deterministic breeding result.  
> PML does not ask Nintendo Crypto until the generic Pokémon constructor actually needs an unresolved random field.

So:

### Before pickup

Already available or reproducible:

```text
eggSeed
IV
Nature
Ability
Gender
EC
Masuda/Charm PID
```

Not yet naturally generated:

```text
ordinary PID
HeightScalar
WeightScalar
```

### During pickup

The PML → Nintendo Crypto calls occur while `main+0x777F40 / main+0x7667A0` is building the final Pokémon object.

### After constructor returns

The final PK8 contains the resolved PID / Height / Weight and those values remain fixed through hatching.

## 20. Important hook points

For tracing natural PML timing:

```text
main+0x7668C0   ordinary PID fallback call site
main+0x766F04   Height resolver call site
main+0x766F14   Weight resolver call site
main+0x7D1320   raw Crypto provider
main+0x7D1360   bounded Crypto provider
```

For observing EggCreateParam just before PML construction:

```text
main+0x789668
```

This is immediately after:

```text
main+0x789664
BL main+0x789770
```

and before:

```text
main+0x7896F0
BL main+0x777F40
```

This makes `main+0x789668` the ideal boundary between:

```text
eggSeed deterministic domain
```

and:

```text
generic PML construction / Nintendo Crypto domain
```.
